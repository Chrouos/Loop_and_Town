# Chapter 2｜活下來的人

這章的功能不是讓玩家「救成功」。

而是第一次證明：

> 改變第一輪死者的行程，不等於解決 18:31。

同時必須避免另一個錯誤理解：

> 若晴被救，所以系統自動選柏勳替死。

不是。

柏勳死亡必須來自新的 Schedule / Location / Failure Path 因果鏈。

---

# Player-facing 規則

本章遵守：

- World Event ≠ Player Knowledge
- 只有實際 Perceive 的內容才能被玩家知道
- persistent gameplay record 由玩家 optional Memory Capture
- 系統不自動發 Event / Truth / Invariant Card
- 玩家自己在 Investigation Wall 比較不同 Loop

---

# 玩家進入這一輪時知道什麼

玩家帶進來的不是 Author Timeline。

而是上一輪真正經歷／Capture 的內容。

可能只有：

```text
若晴去過舊車站
18:31 若晴死亡
柏勳當天下午行蹤可疑
```

如果玩家上一輪沒看到柏勳，就不能憑空獲得他的完整時間線。

最自然的嘗試是：

> 不讓若晴去舊車站。

---

# 若晴為什麼原本會去？

玩家不能直接按：

```text
[阻止若晴]
```

必須先理解她自己的原因。

目前 Canon：

1. 柏勳要處理一批知夏留下、一直未公開的資料
2. 若晴本來就在確認知夏留下的一部分事情
3. 她對自己的攝影、咖啡店工作與未來仍然沒有真正做出決定

第三點尤其重要。

舊版：

> 若晴已經決定今天辭職、離開灰潮鎮。

已撤回。

最新版若晴的核心正是：

> 她有很多留下或離開的理由，但一直讓「責任」替自己回答。

所以玩家不能把「救她」和「幫她離開小鎮」當成同一件事。

---

# 路徑 A｜讓若晴自己改變今晚安排

```text
玩家理解她的攝影 / 知夏資料線
→ 沒有用「知夏一定希望妳怎樣」壓她
→ current-loop trust / respect 足夠
→ 若晴願意說出舊車站安排
→ 玩家提供新的資訊或風險
→ 若晴自己決定暫時不去 / 改時間 / 改交付方式
```

這條路的核心不是說服成功率。

而是：

> 玩家提供資訊，若晴仍然自己做決定。

---

# 路徑 B｜現實條件讓行程改變

也可能不是說服。

例如：

```text
家庭臨時狀況
咖啡店工作事件
交通中斷
其他當輪人物行動
↓
若晴無法照原路線前往舊車站
```

這種改變未必提高 Relationship State。

玩家只是改變了因果條件。

---

# Worldline 改寫

Baseline：

```text
17:40 柏勳離院
→ 18:05 柏勳與若晴碰面
→ 柏勳交付資料
→ 若晴仍留在舊車站區域
→ 18:31 Failure Path A
→ 若晴死亡
```

Chapter 2 Variant：

```text
若晴行程改變
→ 18:05 柏勳抵達但原交付無法照常完成
→ 柏勳決定自行處理 / 帶回資料
→ 回程路線因此改變
→ 18:24 進入另一個設備 / 維修路徑
→ 18:31 Failure Path B
→ 柏勳死亡
```

這是 Author Causality。

重點：

```text
若晴存活
≠
系統選柏勳死亡
```

而是：

```text
若晴行程改變
→ 柏勳自己的下一個決定改變
→ 位置改變
→ 18:31 時接觸到不同 Failure Path
```

具體 18:31 Cascade 技術鏈仍以後續 Mechanism Canon 為準。

---

# 18:31｜第二種死亡

現場應同時容許「事故」與「異常」解釋。

例如可以暫時呈現：

```text
舊站 / 維修區設備短暫異常
→ 通道或電力狀態改變
→ 柏勳受致命傷
```

但不要過早把某一台設備定義成所有世界線的單一事故核心。

Author 可以知道兩輪有相似與不同：

```text
相似：
18:31
局部設備異常
某些同步症狀

不同：
人物位置
接觸設備
死亡者
前置行程
```

Player 必須真的 Perceive / Capture，才有材料比較。

---

# 若晴活下來之後

若晴不能變成「成功救援動畫」。

18:31 過後，她仍然有自己的人生問題。

她可能重新回到：

- 咖啡店工作
- 母親照護
- 《退潮以後》作品集
- 外地攝影機會
- 是否要繼續留在灰潮鎮

但她**不會因為被救就自動得到答案**。

20:30 可以是一個很安靜的 Character Moment。

例如店長問她：

> 「妳那個外地的事情，想好了嗎？」

若晴可能只回答：

> 「還沒有。」

這反而更符合她。

她活下來了。

但：

> 活下來 ≠ 人生問題被解完。

---

# Player 可感知的 Moments

## Moment A｜若晴仍然活著

如果主角真的確認她的狀態：

```text
18:31 後
若晴存活
位置：依本輪 route
```

可以 Capture，也可以不 Capture。

## Moment B｜柏勳死亡

如果親眼看到：

```text
18:31
柏勳倒下
附近設備狀態異常
```

Memory 只能保存真正感知到的部分。

如果只是事後聽人轉述，就只能保存轉述。

## Moment C｜18:31 又出現

玩家可能自己產生：

> 「又是 18:31？」

系統不能替玩家升級成：

```text
[Invariant]
18:31 = 真相
```

---

# Investigation Wall

如果玩家真的 Capture 到足夠資訊，可能自行排列：

```text
Loop 01
若晴死亡 · 18:31

Loop 02
柏勳死亡 · 18:31
```

玩家可以自己連線、寫 Note。

這是 hypothesis，不是系統答案。

---

# 延遲後果

## 志遠

柏勳死亡與五年前知夏案出現相似異常後，他更難繼續把事情視為普通案件。

但仍不代表他立即公開未登錄證物。

## 庭安

柏勳路線改變，也會影響她對研究資料與醫療資料的下一步安排。

## 予安

如果玩家整天要求他幫忙，他可能錯過自己的房仲約。

```text
主角試圖救人
→ 同時改變朋友原本的人生行程
```

這是後續倫理主題的早期體驗。

---

# Chapter 2 章末

Author Truth 可以是：

```text
Loop 01
若晴 → 18:31 死亡
柏勳 → 存活

Loop 02
若晴 → 存活
柏勳 → 因 changed route 進入不同 Failure Path
       → 18:31 死亡
```

玩家要自己逼近這個比較。

這一章真正推翻的是：

```text
「只要把第一輪死者移開就好了」
```

而不是建立新的錯誤規則：

```text
「每輪系統都一定會換一個人死」
```

如果玩家已經找到知夏留下的手錶刻字：

> 如果你第二次看見 18:31，
> 不要先救第一個死者。

這句話此時才開始有新的意義。

但它不是系統 Tutorial，也不保證知夏當年的判斷就是最終真相。

---

# Event Graph 最小需求

Author Graph 應表達完整中間因果：

```text
wakaharu_reveals_station_plan
→ player_changes_conditions
→ wakaharu_route_changes
→ boxun_arrives_without_expected_handoff
→ boxun_decides_new_route
→ boxun_enters_failure_path_b
→ convergence_1831
```

並保留其他 delayed effects：

```text
boxun_dead
→ tingan_replans

yuan_busy_with_player
→ realtor_meeting_missed
```

不能寫成：

```text
wakaharu_saved
→ boxun_dead
```

那會把真正的 Event Graph 又退化成「替死鬼切換器」。
