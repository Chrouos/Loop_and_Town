# 灰潮鎮：玩家端第一個輪迴設計

日期：2026-09-23
狀態：待審閱
基底：`main` 的 Worldline Simulator v0.1、`story/` 與 Event Graph Viewer

## 1. 目的與驗收邊界

做出可在瀏覽器持續遊玩的第一個縱切章節。玩家透過安靜的檔案敘事認識事件，自行選取少量證據、在期限前採取行動，離開後小鎮依現實經過時間推進。隔天回來能比較自己親歷或取得紀錄的世界線，檢查「18:31 固定，結果可變」這個假設。

這次只實作現有資料可支持的 18:31 車站事件與 21:14 延遲後果。這是一個可重玩、可比較的短篇原型，不聲稱無限劇情或已完成 NPC 自主生活。

## 2. 專案邊界與選擇

在同一 repo 新增玩家端應用；`tools/event-graph-viewer` 保留開發者工具定位。玩家端與 Viewer 共用 `story/` 定義及無 React 相依的 Simulator，不把兩份劇情邏輯複製到不同網站。

共用層負責讀取並驗證故事定義、從固定初始狀態重播已確認的行動、取得 World State 和 append-only Worldline History。玩家端另外負責現實時間、玩家知識、文件敘事、存檔與演出。Simulator 的完整歷史只供運算，不直接當玩家閱讀內容。

不在這次重構 Viewer 視覺、增加自由輸入指令、生成式 NPC、多人或後端帳號同步。先讓第一條因果鏈真正可玩，再擴充 Event Graph。

## 3. 玩家流程與文字

開場從死者來信開始：黑底分段文字，信封在敘事提及寄件人後進入畫面，拆信有清楚可按且可用鍵盤操作的入口。閱讀頁只呈現文件當事人當時可能知道的內容，來源、形成時間及取得原因可查，但不把推論寫進原始文件。

玩家可從文件中挑選最多六段證據放到可自由排列的推理桌。連接兩段後仍需選擇「目前最多能支持哪個說法」；猜測過度不儲存為事實。文案區分觀察、通報、醫療推定和玩家假設。推理桌與案卷按需要打開；主畫面維持大量留白與安靜閱讀。關鍵動態僅用於拆信、回覆抵達、18:31 記錄改寫及午夜重置，並支援跳過與 reduced motion；無自動播放聲音。

介入方式以劇情中可交代的行動呈現，玩家能在 18:20 前選擇保護若晴、設法攔住醫生、兩者都做，或不介入。每個選擇須說明玩家本人做了什麼、予安若有協助做了什麼，但不預告 18:31 的結果；UI 不使用「選擇分支」「指派任務」等後台用語。選擇會在截止時確定，過期不能回填為先前已做的事。

## 4. 現實時間與模擬映射

第一次開啟時，將當下真實 timestamp 記為本機錨點，對應虛構當日 18:00。之後每經過一分鐘現實時間，虛構時間前進一分鐘：20 分鐘後為介入截止 18:20，31 分鐘後為 18:31，3 小時 14 分後為 21:14，6 小時後到午夜。午夜接續下一輪；後續每輪為 24 小時。這讓任何時區的玩家都能從可操作的開場開始，且關閉頁面不暫停進度。畫面會清楚標示鎮內時間及本輪下一個可預期的聯絡時間，避免誤認為裝置所在地時鐘。

運算時以錨點和當前 timestamp 算出輪次與虛構時間。到 18:20 前保存玩家已確認的行動；到 18:20 才按固定順序將兩個現有 action ID 套入 Simulator，之後只 `runUntil` 到已經過的時間。18:31 和 21:14 的結果由 Simulator 的 State、Queue 和 History 決定，UI 不另寫一份 if/else 結局。午夜存下該輪實際運算結果和玩家當時已得知的資訊，再以原始世界狀態開始下一輪。

跨多日離線時依輪次逐輪確定重播；沒有新的行動視為不介入。回訪顯示簡短的離線報告，只說明有可閱讀的消息和時間，不一次洩漏所有世界真相。對同一錨點、行動及時間反覆開頁，事件及報告只產生一次。裝置時鐘回撥不逆轉已確認的歷史；偵測到異常時保留上次確認的進度並顯示簡短提示。本機存檔無法防止刻意修改時鐘或跨裝置失同步，列為此版限制。

## 5. World Truth、Player Knowledge 與文件

`World Truth` 由 `story/` 與 Simulator 決定，包含角色狀態、事件 variant、延遲效果和完整歷史。`Player Knowledge` 是另外的持久化紀錄：已打開的文件、來源與取得時間、已看過的消息、玩家挑選的摘錄、已作出的推論及每輪已知事件。渲染只讀 Knowledge；不根據完整 World Truth 自動顯示角色死亡或記者失蹤。

每個可見敘事節點都有明確的揭露時刻和來源。例如 18:31 事件先顯示「車站的燈熄了」，鎮內通報或予安目擊要在約定時間抵達後才加入案卷；21:14 的世界狀態變化也須等實際收到消息後才可讀。若玩家未介入，不能寫成「玩家選擇放任死亡」；未知身分或因果維持未知。

第一版文件清單與其解鎖條件在獨立資料檔明列，引用 Event ID / Variant ID / Action ID，不用從 UI 文案反向判定劇情。每一份文件須有作者、形成時間、取得時間、正文及可引用的證據片段。情節文字逐條校對說話者、知情範圍、時間、語氣與是否劇透。

## 6. Event Card、輪次與比較

18:31 保持同一個 Event ID，每輪記錄其實際 variant。跨輪比較只能顯示玩家已知道的結果；不知道的欄位顯示「尚未查到」，不能從 Simulator 偷看。玩家至少完成兩輪後，可把兩份已取得的紀錄放在一起，指出變動的是死者或現場狀態，並提出「18:31 仍出現」這個候選 Invariant；系統區分「觀察到兩次」與「已證明永遠不變」。

21:14 的後果在有因果線索前只呈現失蹤與前一事件的時間順序，不能替玩家宣告若晴死亡必然導致記者失蹤。Viewer 的完整 Diff 仍供作者除錯；玩家版只展示已知資料。

## 7. 存檔與遷移

存檔欄位至少含 `version`、`anchorTimestamp`、`lastConfirmedTimestamp`、逐輪已確認 action IDs、已揭露記錄 ID、文件閱讀狀態、推理桌位置與連線。所有 action / event 引用需驗證是否仍存在於當前 story 定義；重複、損壞或缺欄位存檔應安全修復並保留可辨識的玩家知識。

目前另有已發布的案卷版使用舊 localStorage key。若新舊站同源，可在玩家端提供一次性讀取並匯入；若不同源，先提供明確的存檔匯出／匯入流程，不假設能跨網域讀取 localStorage。只把可辨識的文件、摘錄和推論映射進 Knowledge，無法證實的舊「結果」保留為個人筆記。匯入不回填 Simulator 的行動或偽造世界線。舊站是否切換到新站屬另一個發布步驟，須在相容驗證後決定。

## 8. 驗收情境與測試

必須以同一 `story/` 初始狀態驗證四種行動，在 18:31 / 21:14 得到現有規格的精確結果：

| 已確認行動 | 18:31 | 21:14 |
| --- | --- | --- |
| 無 | 若晴死亡 | 記者失蹤 |
| 保護若晴 | 醫生死亡 | 不發生失蹤 |
| 攔住醫生 | 若晴死亡 | 記者失蹤 |
| 兩者都做 | 無人死亡 | 不發生失蹤 |

另以可控制時鐘測試 18:19 可確認、18:20 截止、18:30 未洩漏結局、18:31 Simulator 已解出結果但玩家只能看到當下可觀察的異常、通報抵達後才揭露可確認的結果、21:14 延遲效果、午夜封存、兩輪比較、多日離線、重複載入與時鐘回撥。測試需驗證世界狀態和玩家可見內容各自正確，不只比對畫面文字。桌面、手機與鍵盤均能完成拆信、選證據、介入、回訪和跨輪比較；減少動態設定下可完整閱讀。

## 9. 待確認的產品取捨

第一次進入的虛構時間固定為 18:00，讓玩家約 20 分鐘後遇到介入截止、約 31 分鐘後看到第一次 18:31 事件；後續輪次依真正經過的 24 小時前進。這是本版最重要的節奏選擇，可在實作計畫前調整。其他行為以上述驗收條件為準。
